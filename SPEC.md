# Deep Dish — спецификация архитектуры

Состояние на 22.11.2026. Развёрнуты клиент 0.7.18 и сервер 0.4.7. Ниже описан кандидат 0.7.19 / 0.4.9, если версия не указана явно. История и статус выпуска — в [плане](PLAN.md), первичные находки — в [аудите](docs/AUDIT.md), дальнейшие задачи — в [бэклоге](docs/BACKLOG.md) и [плане рефакторинга](docs/REFACTORING.md).

## 1. Контуры системы

```text
GitHub Pages → установка и обновление PWA на iPhone
                ├─ React + Dexie/IndexedDB → дневник, расчёты, каталог
                ├─ Workbox → кэш приложения
                ├─ HTTPS → FastAPI + SQLite на домашнем QNAP
                └─ Open Food Facts → поиск по названию и штрихкоду

«Быстрые команды» iPhone ↔ HTTPS API QNAP ↔ локальная база SQLite
```

Ввод, правка, локальный поиск, расчёты, графики и экспорт используют данные на устройстве. Сервер и профиль для первого запуска не обязательны. Внешний справочник, синхронизация и мост Apple Health зависят от связи. Для офлайна нужна установленная и закэшированная сборка, для истории — сохранное хранилище браузера. Установка на iPhone и поведение iOS при очистке хранилища проверяются отдельно от настольного браузера.

## 2. Модель питания

- **Продукт** хранит название, бренд, категорию, КБЖУ на 100 г или на порцию, штрихкод и типовые порции.
- **Рецепт** хранит ингредиенты, их количества и выход готового блюда. Вводить готовое можно в граммах или в порциях.
- **Сохранённый приём пищи** — личный именованный набор продуктов, который можно внести повторно. Текущая реализация сохраняет позиции типа «продукт» и пропускает рецепты.
- **Запись дневника** хранит дату, приём пищи, время еды, время создания, ссылку на продукт или рецепт, количество, единицу и КБЖУ внесённого количества. Количество для порционных записей кодируется как число порций × 100 в поле `grams`. Новая запись использует сохранённую единицу при редактировании и экспорте. При миграции старой записи Dexie берёт доступную единицу из каталога.
- Четыре стандартных приёма — завтрак, обед, ужин и перекус. В настройках задаётся время, которое участвует в автоматическом выборе приёма. Интерфейса добавления и переименования приёмов в 0.7.18 нет.
- Каталог включает встроенную базу из `data/products_v2.json`, собственные, семейные и сохранённые из OFF позиции. Недавние совпадения поднимаются в выдаче. Звёзды сняты с интерфейса в 0.7.14.

## 3. Модель данных

| Сущность | Локальное хранение | Обмен |
|---|---|---|
| Продукты и рецепты | `foods`, `recipes` | Общий каталог по правилам `isPublic` и владения |
| Дневник и вес | `entries`, `weightLogs` | Личные записи. Приём помеченного как удалённый объекта передаётся через `deletedAt` |
| Приёмы и шаблоны | `slots`, `savedMeals` | Личный обмен. Совпадение ID слота у двух участников допускается |
| Профиль | `profiles`, ключ `local` | Личный, на сервере ключ участника |
| Дневные нормы | `dayNormas`, ключ `date` | Синхронизируются по `updatedAt` в рамках участника |
| Пометки «не учтён» | `slotMarks` | Участвуют в расчёте, синхронизируются в рамках участника и входят в архив |
| Достижения | `achievements` | Активные достижения видит семья. Локальные и серверные ID автора требуют согласованного отображения |
| Продуктовые события | `events` | Попутная отправка в серверную таблицу `events` |
| Тема, часть настроек и подключение | localStorage | На устройстве |

В IndexedDB применяются миграции Dexie. Версия схемы 8 добавляет `syncReceipts`. SQLite хранит документы в `items` с первичным ключом `(kind, id, owner)` и отдельным уникальным ограничением для общего каталога, достижений и кэша OFF. Участники и токены хранятся в `users`. Новые ID дневника преимущественно UUIDv7. Схемы клиента и сервера связаны преобразованиями в `sync.ts` и `server.py`. Миграция переносит доступные строки. Она не может восстановить старые данные, которые уже исчезли с сервера и которых нет в резервной копии или на устройстве.

## 4. Синхронизация

- `POST /sync` с bearer-токеном принимает `since`, `changes`, `events`, `client_now`. Новый клиент использует составной `cursor` `(applied, kind, id, owner)` и флаг `pull: false` для порций отправки. Ответ содержит `results`, следующий `cursor`, `hasMore` и поля старого протокола. Для старого числового курсора сервер выдаёт пограничную группу одинакового времени целиком.
- `applied` монотонно увеличивается на сервере. `updatedAt` помогает разрешать конфликт версий, а `baseUpdated` позволяет применить правку известной версии при отставших часах устройства. При конфликте сервер возвращает актуальную запись. Клиент сохраняет правки, сделанные во время передачи, до следующей отправки.
- Клиент отправляет пачки до 1000 записей и 500 событий, затем читает страницы до `hasMore: false`. В IndexedDB атомарно сохраняются принятые изменения и подтверждения по записям. Отклонённые изменения остаются в очереди. Одновременные попытки в одной вкладке объединяются, Web Locks при наличии сериализует обмен между вкладками.
- Запуск приложения, открытие видимой вкладки, возврат сети, таймер в открытом приложении и ручная кнопка инициируют обмен. Пауза сохраняет привязку дневника к тому же участнику.
- Сервер сохраняет отметки удаления. Явное удаление продукта (`delBy=user`) защищено от возврата старой копии. Для прежних ложных отметок каталога есть ветка восстановления.
- Личные записи читаются и записываются по владельцу из токена. Общий каталог следует правилам видимости, семейные достижения видны в ленте.

## 5. API NAS

| Путь | Назначение |
|---|---|
| `POST /register` | Первый участник становится администратором. Следующие используют приглашение. Старый клиент временно поддерживается через `adminToken` |
| `POST /sync` | Дневник, каталог, достижения, профиль и доставка событий |
| `GET /healthz`, `GET /backup-healthz` | Живость и состояние резервирования |
| `GET /admin/users`, `GET /admin/metrics`, `GET /admin/telemetry` | Участники без токенов, семейные агрегаты, техническая диагностика |
| `POST /admin/push-catalog` | Переиздание каталога для следующего обмена |
| `POST /admin/invite` | Одноразовое приглашение с действием 15 минут |
| `GET /off/search` | Серверный поиск в Open Food Facts |
| `POST /health/code`, `GET /health/setup` | Выдача или замена кода моста, инструкция по настройке |
| `POST /health/weight`, `GET /health/day` | Импорт массы и выдача суточной суммы калорий. Доступ по отдельному коду моста |

Мост пишет вес в SQLite и передаёт его на устройство через синхронизацию. Сумма калорий берётся из уже синхронизированных записей на NAS. «Быстрые команды» запускаются на iPhone. Проверка повторного запуска, поздних правок и локального дня входит в приёмку. [Контракт моста и статус](docs/APPLE_HEALTH.md)

## 6. Инфраструктура NAS

FastAPI обслуживает Uvicorn с TLS. Docker Compose использует локальный сертификат и SQLite в WAL с `synchronous=FULL`. Главный сценарий — доверие сертификату на iPhone и доступ из домашней сети. Доступ через Headscale записан в дорожной карте. Текущий Compose обслуживает TLS напрямую.

Сервер 0.4.7 создаёт проверенные снимки SQLite, публикует их атомарно, хранит 30 поколений и сообщает о свежести и сбоях. Снимок делается примерно раз в шесть часов. Рабочий статус этой функции и восстановление из независимого носителя проверяются отдельно. [Эксплуатация](backend/README.md)

## 7. Норма и вес

- Базовая модель использует формулу Миффлина–Сан Жеора или ручной TDEE. Тип профиля содержит вариант Кэтч–МакАрдла, но отдельной ветки расчёта сейчас нет. Темп и выбранная цель задают поправку. Ограничение в коде — минимум 1,1 × BMR.
- Для адаптации выбирается свежее пригодное 28-дневное окно из истории примерно за 120 дней, с шагом 7 дней и минимум 21 днём записей. Дни, отмеченные как неучтённые, исключаются. Среднее калорий рассчитывается по учтённым дням. Поправка по весу делится на длину всего окна. Адаптивная часть ограничена ±350 ккал от базового TDEE. Ограничение изменения нормы по неделям записано в историческом плане.
- Дневная норма фиксируется при первом открытии соответствующей даты. Снимок, впервые рассчитанный задним числом, отмечается `retro`. Сегодняшнее значение пересчитывается при сохранении профиля. Ретроспективный расчёт использует вес по дату расчёта включительно и текущий профиль.
- Кольцо цели по темпу сравнивает тренд с планом. В режиме целевого веса кольцо показывает прогноз к дате из среднего темпа от старта. Условия применимости и дата измерений должны быть понятны при чтении пояснения.

## 8. Фронтенд

Навигация разделяет «Сегодня», «Профиль», «Семью» и «Настройки». Основное действие «＋ еда» закреплено рядом с итогом дня. Добавление по конкретному приёму, поиск, типовые порции и календарь описаны в [сценариях](docs/USER_SCENARIOS.md). [Визуальный канон](docs/DESIGN.md) хранит требования к карточкам, панелям, кольцам, цветам и размерам текста.

Поиск по названию, штрихкоду или локальному каталогу начинается на телефоне. Онлайн-выдача OFF визуально отдельная. Камера подключается через ZXing, модуль загружается отдельным блоком. Для офлайн-проверки КБЖУ применяется соотношение 4/4/9 с порогом 15% и отдельным случаем алкоголя. Проверку и результаты поиска OFF следует отличать от валидации КБЖУ.

## 9. Онбординг, мотивация и семейный обмен

Онбординг состоит из приветствия, объяснения ввода, необязательного профиля и установки на экран «Домой». Справка доступна из настроек. Настройка Home CA и Apple Health выполняется по отдельной инструкции.

Баннеры похвалы и предупреждения показываются внутри приложения. Детектор выделяет часы с признаком «красной» категории в трёх разных днях за 60 дней. Исторические записи с приблизительным временем исключаются. Факты и достижения описаны в [отдельном каноне](docs/FACTS.md).

### Продуктовые метрики

Клиент добавляет события в IndexedDB, при синхронизации отправляет их порциями. Семейную витрину читает администратор. Новые диагностические события не содержат текста запроса OFF и значения ручного веса. Витрина использует булевы поля JSON для счётчиков онлайн и офлайн и рассчитывает тренд веса по участникам. Исторические события, срок хранения, согласие участника и удаление событий остаются отдельной задачей.

### Обмен результатами между пользователями

Согласованная модель 0.8.0 включает разовый обмен агрегатами и подписки на недельные сводки. В 0.7.18 есть лента достижений, адресный обмен сводками и подписки запланированы.

- Отправитель включает видимость и выбирает уровень. Полный режим включает тренд веса, регулярность и прогресс к цели. Режим «без веса» — регулярность и относительный прогресс.
- Получатель выбирает участников для подписки. Отправитель уведомляется о новых подписках.
- Разовая отправка из своего отчёта выбирает конкретного получателя. Дневниковые позиции в сводку не входят.
- Доставка планировалась как панель в приложении с авто-скрытием после трёх действий. Челленджи отложены.
- Предложенный контракт и порядок реализации описаны в [бэклоге](docs/BACKLOG.md).

## 10. Экспорт, импорт и очистка

- JSON v2 включает продукты, рецепты, шаблоны, приёмы, записи, вес, нормы, профили, достижения и пометки «не учтён». Токены подключения, настройки устройства и события хранятся отдельно.
- Импорт читает JSON v1 и v2, проверяет файл до записи и применяет данные одной транзакцией. Более новые локальные версии сохраняются. Полное восстановление на чистом устройстве сохраняет привязку к владельцу архива. Архив не предоставляет доступ к серверу. Для переноса между участниками доступен импорт каталога.
- CSV содержит записи еды с сохранённой единицей количества и экранирует текстовые ячейки.
- «Очистить данные на этом устройстве» очищает локальные таблицы и привязку, затем возвращает встроенный каталог. Аккаунт и история NAS управляются отдельно.
- MyFitnessPal CSV конвертируется отдельным инструментом [mfp2dd.mjs](tools/mfp2dd.mjs). Интерфейс штатного импорта принимает JSON.

## 11. Границы и приёмка

- Функциональный критерий — холодный запуск установленной PWA, сохранение еды офлайн и последующий обмен без потерь. На iPhone дополнительно проверяются камера, клавиатура, VoiceOver, разрешения и Apple Health.
- Данные продуктов, веса и профиля считаются личными. Внешний справочник получает запрос или штрихкод, NAS хранит семейную историю и размещает её временные и резервные копии.
- Проверка подключения, резервирования и сценариев обмена описана в [чек-листе выпуска](tools/release.md). База фактических дефектов и границы проверок находятся в [аудите](docs/AUDIT.md).
