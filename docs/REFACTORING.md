# План рефакторинга Deep Dish

Цель — сохранить рабочий дневник и ускорить безопасные изменения. Границы работы определяют сохранность данных, быстрый мобильный ввод и воспроизводимый выпуск. [Аудит](AUDIT.md) · [Бэклог](BACKLOG.md)

## Этапы

| Этап | Работа | Критерий завершения |
|---|---|---|
| 1. Стабилизация обмена | Устойчивый курсор выдачи, подтверждение по каждой записи, локальная фиксация подтверждений, личные ключи на сервере, сохранение удаления в каталоге. | 5001 запись доставляется двумя страницами, прерванная отправка 2001 записи возобновляется, изменения двух участников не смешиваются. Проверены старый клиент и копия старой схемы. |
| 2. Перенос и восстановление | Граница архива в `src/data-transfer.ts`. Атомарный импорт, ясное назначение CSV и JSON, отдельный импорт каталога, локальная очистка с отключением семейного обмена. | Экспорт восстанавливает дневник, нормы, флаги приёма и достижений в чистом профиле. Ошибка в последней таблице сохраняет прежнюю базу. Проверена изолированная копия QNAP. |
| 3. Контракт синхронизации | После выпуска первого исправления отделить транспорт клиента, применение страниц и ведение подтверждений. На сервере отделить миграции и SQLite-запросы от маршрутов. Сохранить контракт для старого клиента на время обновления семьи. | Рефакторинг проходит те же сценарии без изменений видимого поведения. Откат испытан на копии с сервером и клиентом предыдущего выпуска. |
| 4. Общие мобильные компоненты | Проверять семантику панелей, фокус, ввод количества и повторную запись общими сценариями. Выделять компоненты из больших экранов только по проверенным сценариям. | Основной путь проходит в обоих режимах темы, на узком экране, с клавиатуры и на iPhone с VoiceOver. |

## Выпуск 0.7.19 / 0.4.9

22.11.2026 восстановление из OneDrive и миграция отдельно от рабочего приложения пройдены. Сервер и клиент опубликованы. Приёмка на iPhone остаётся открытой. [Результаты выпуска](../PLAN.md)

1. Взять согласованный снимок SQLite и manifest с резервного носителя QNAP. Сверить пару, сохранить отдельно последнюю рабочую версию файлов сервера, подтвердить восстановление в отдельном экземпляре.
2. Проверить миграцию старой схемы и обмен на отдельном порту. Сверить количество записей до и после, доступность Health API и старого клиента.
3. Выпустить сервер 0.4.9, затем клиент 0.7.19. Проверить версию и резервирование сервера, сборку GitHub Pages и обмен сначала с тестовым, затем с рабочим приложением.
4. После выпуска провести контроль iPhone и закрыть найденные регрессии. Приёмка подписанной команды Apple Health зависит от доступности Apple-устройства.

Цена ошибки в первом этапе — перезапись семейного дневника. До подтверждённого восстановления миграцию на единственном рабочем экземпляре не запускают. [Установка и откат](../backend/README.md)
