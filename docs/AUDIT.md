## Целостность и архитектура

| ID | Наблюдение и эффект | Основание |
|---|---|---|
| A01 | **Критично. Потеря хвоста серверной выдачи.** Одной пачкой приняты 5001 обычная запись с одинаковым серверным временем. Клиент получает 5000 строк, следующая страница пуста. Курсор по времени перескакивает через остаток с тем же временем. | Воспроизведено. [Выборка и курсор](https://github.com/lichmanenko/deep-dish/blob/27e1f9aa236788a6b058ab68d6da2f1bcc3634fa/backend/server.py#L717). |
| A02 | **Критично. Личные настройки конфликтуют.** У двух участников с разным временем завтрака ожидается по одному личному слоту. А после обмена не получил свой слот, Б получил свой. Причина — одинаковый стандартный ID и глобальный ключ SQLite `(kind,id)`. Чтение записей дневника с разными ID разведено, запись требует проверки владения. | Воспроизведено на обычном редактировании настроек. [Схема](https://github.com/lichmanenko/deep-dish/blob/27e1f9aa236788a6b058ab68d6da2f1bcc3634fa/backend/server.py#L88) · [стандартные слоты](../src/db.ts#L277). |
| A03 | **Критично. Отправка может терять изменения.** Лимит 2000 берётся в порядке основной таблицы, граница вычисляется по времени изменений. Старый ID с новой правкой и одинаковые отметки времени на границе ломают предположение об упорядоченности. Отдельный случай — правка во время обмена до присвоения `lastPush`. Суммарный `rejected` не удерживает запись в очереди. | Ревью кода. [Выборка и применение](../src/sync.ts#L59) · [границы](../src/sync.ts#L149). |
| A04 | **Высоко. Конкурентные обмены и восстановление могут обходить очередь.** Ручной, автоматический и административный обмен могут пересечься. Входящие изменения применяются по одному, затем курсоры записываются в localStorage. Полная перезагрузка продолжает загрузку даже после неуспешного предварительного обмена. | Ревью кода. [Клиент обмена](../src/sync.ts#L120) · [fullReload](../src/sync.ts#L175). |
| A05 | **Высоко. Старая живая версия возвращает осознанно удалённую карточку.** Удаление видно другому участнику. Повтор старой карточки от владельца снова делает её активной. Это отличается от корректного восстановления старых служебных отметок удаления. | Воспроизведено. [Разрешение удаления](https://github.com/lichmanenko/deep-dish/blob/27e1f9aa236788a6b058ab68d6da2f1bcc3634fa/backend/server.py#L660). |
| A06 | **Критично. JSON-импорт бывает частичным.** Тестовый файл содержал допустимую карточку продукта и повреждённую карточку рецепта. Интерфейс сообщил об ошибке, а продукт остался в каталоге. Формат проверяет заголовок, запись идёт по таблицам без общей транзакции. Импорт в подключённом клиенте также требует явного решения, как восстановленные строки должны попасть в исходящую очередь. | Воспроизведено в браузере. [Импорт](../src/store.ts#L573). |
| A07 | **Высоко. Экспорт и очистка обещают больше, чем делают.** JSON не сохраняет отметки «не учтён», достижения и настройки. Дневные нормы присутствуют при экспорте, но пропускаются импортом. Очистка сохраняет часть локальных таблиц и связь с NAS, серверные данные остаются. CSV не экранирует разделитель, кавычки и переносы в пользовательских названиях, а для порций выводит условные граммы. | Ревью кода. [Экспорт и очистка](../src/store.ts#L498) · [настройки данных](../src/screen-settings.tsx#L96). |
| A08 | **Высоко. Нормы и пометки не восстанавливают одинаковое состояние устройств.** У нормы нет `updatedAt`, а `slotMarks` отсутствуют в обмене. После переустановки или при использовании двух устройств участник может увидеть иной расчёт для той же истории. | Ревью кода. [DayNorma](../src/db.ts#L92) · [таблицы обмена](../src/sync.ts#L18) · [импорт](../src/store.ts#L573). |
| A09 | **Высоко. Подключение говорит о прошедшем обмене даже при частичном отказе.** Автосинк запускается при старте и `online`, ограничитель в 5 минут не создаёт таймер повтора. Обнаружить накопленные изменения или причину невыполненной отправки из основного экрана трудно. | Ревью кода. [Триггеры](../src/App.tsx#L49) · [автосинк](../src/sync.ts#L187) · [сообщение семьи](../src/family.tsx#L66). |

Рекомендуемое архитектурное изменение — версия протокола с устойчивым курсором выдачи и подтверждаемыми исходящими изменениями. SQLite, IndexedDB и существующие экраны для этого подходят. Главный риск — миграция уже используемого дневника при одновременной работе старого и нового клиентов. Нужны испытание на обезличенной схеме данных, план повторной сверки и проверка отката.
