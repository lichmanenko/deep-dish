# Deep Dish sync — сервер семейной синхронизации

FastAPI и SQLite в WAL с `synchronous=FULL`. В серверном обмене есть личные записи, общий каталог, достижения и события. [Протокол и модель данных](../SPEC.md#4-синхронизация)

## Установка на QNAP

1. Разместите рядом файлы `server.py`, `sqlite_backups.py`, `requirements.txt` и `compose.yaml` из одной ревизии. Сверьте пути монтирования в Compose с каталогом приложения на NAS.
2. В каталоге `data` разместите `server.crt` и `server.key`. Укажите в сертификате адрес, по которому iPhone будет обращаться к NAS. Сохраните отдельно существующую БД и рабочие сертификаты перед обновлением.
3. Создайте приложение из Compose в Container Station или запустите `docker compose up -d` из его каталога. Текущий Compose запускает Uvicorn с TLS на порту 8687 и устанавливает Python-зависимости при старте.
4. С доверенного устройства проверьте `https://<адрес-NAS>:8687/healthz` и `/backup-healthz`. Версию API показывает поле `info.version` в `/openapi.json`.

## Обновление с 0.4.7 до 0.4.9

Сервер 0.4.9 меняет ключ SQLite `items` на `(kind, id, owner)`. Миграция выполняется при запуске одной транзакцией. Старый сервер использует прежний ключ в `ON CONFLICT(kind, id)`, поэтому запускать его на мигрированной базе нельзя.

1. На NAS возьмите согласованную пару `.db` и `.db.json` с резервного носителя. Сверьте SHA-256 и `PRAGMA quick_check`. Сохраните комплект серверных файлов и конфигурации текущего выпуска.
2. Восстановите отдельную копию БД на NAS. Запустите `python tools/check_restore.py <путь-к-.db.json> --scratch <отдельный-каталог>` из комплекта 0.4.9 с установленными зависимостями. Скрипт сверяет SHA-256, ключи, целостность и число записей до и после миграции на временной копии. Проверку записи через старый и новый протокол выполните на отдельной синтетической базе.
3. Перед обновлением остановите рабочий сервис и снимите согласованную точку отката. Запустите новый сервер и подтвердите `info.version`, `/healthz`, свежую копию и обмен старого клиента. Затем выпускайте клиент 0.7.19.
4. При откате остановите обмен и сохраните мигрированную БД отдельно. Восстановите согласованную точку отката и комплект 0.4.7. Сохраните все записи, пришедшие после точки отката, для сверки и адресного восстановления. Новый клиент в период отката оставьте на паузе до проверки восстановления и курсоров.

## Подключение с iPhone

1. Установите профиль доверенного локального CA. Включите полное доверие для его корневого сертификата в системных настройках iPhone.
2. В приложении откройте **Семья**, введите HTTPS-адрес и имя. Первый участник становится администратором. В 0.7.19 / 0.4.9 администратор выдаёт отдельное одноразовое приглашение сроком на 15 минут.
3. После подключения используйте «Синхронизировать». Автоматический обмен запускается при открытии, восстановлении сети и по таймеру в открытом приложении.
4. В разделе «Мост Apple Health» получите код для «Быстрых команд». Нажатие «Обновить» заменяет код. Сумма калорий в API отражает уже синхронизированный дневник. [Состояние моста и контракт](../docs/APPLE_HEALTH.md)

## Доступ и диагностика

- Токен администратора даёт доступ к его дневнику и админ-функциям. В 0.7.18 приглашение копировало этот токен. Новый интерфейс генерирует отдельное приглашение через `POST /admin/invite`, прежний параметр регистрации поддерживается для старого клиента. `/admin/users` возвращает сведения об участниках без токенов.
- «Приостановить синхронизацию» останавливает обмен на устройстве и сохраняет привязку к участнику. Серверный токен действует и после паузы. Доступ из внешней сети относится к отдельной задаче.
- Ошибка проверки TLS требует сверить адрес в сертификате, срок действия и доверие корневому CA на клиенте.
- При проблеме запуска сначала проверьте, что все четыре файла на месте, пути Compose совпадают с реальными и читаются сертификаты. Затем проверьте логи контейнера и состояние `/healthz` и `/backup-healthz`.
- Рабочая SQLite, копии и журналы могут содержать личные данные. Храните их на домашней инфраструктуре и учитывайте их при настройке доступа.

## Локальная разработка

Из корня проекта установите зависимости и запустите приложение с новой SQLite в игнорируемом каталоге. Для Windows PowerShell задайте путь через `$env:DD_DB`.

```sh
python -m pip install -r backend/requirements.txt
DD_DB=tmp/local-api/deepdish.db python -m uvicorn --app-dir backend server:app --host 127.0.0.1 --port 8689
python -m unittest discover -s backend -p "test_*.py"
```

Локальный HTTP подходит для тестирования с браузером на localhost. Для размещённого на Pages клиента используйте HTTPS.

## Резервирование SQLite (сервер 0.4.7)

На NAS нужно обновить server.py и добавить sqlite_backups.py рядом с ним.
requirements.txt не меняется. Compose дополнен healthcheck; существующие данные,
порт, сертификаты, источник и ретеншн HBS сохраняются.

Фоновый worker создаёт копию при отсутствии свежего подтверждённого поколения и затем
каждые 6 часов, независимо от запросов синхронизации. Хранятся 30 поколений. Ошибки
повторяются не чаще раза в 5 минут. Обычный sync остаётся доступным при ошибке backup.

Копия сначала создаётся через VACUUM INTO во staging, проходит quick_check,
foreign_key_check и SHA-256, закрывается/fsync и публикуется os.replace.
Staging и готовый каталог должны находиться в одном mount; при EXDEV операция
завершается ошибкой, копирование поверх конечного файла не используется.
В штатном QNAP Compose это /app/.backup-staging и /app/data/backups;
существующий HBS-источник data включает только опубликованные файлы резервирования.
В Dockerfile без QNAP bind-layout staging расположен в /data/.backup-staging:
при резервировании всего /data этот временный каталог нужно исключить из внешней копии.

Рядом с каждой новой .db есть неизменяемый .db.json с размером/хешем и результатом
проверки. backup-status.json обновляется атомарно раз в минуту. Последний
успешный snapshot не становится свежим от одного heartbeat; сбой не удаляет
старые поколения. После прерванного процесса убираются только собственные
временные файлы с UUID-именами. Старая .last больше не используется.

Контроль:
- GET /healthz остаётся liveness (200) и добавляет технический backup-статус.
- GET /backup-healthz: 200 только при исправном резервировании, иначе 503.
  Нет содержимого дневников, имён пользователей, токенов или полных путей.
- python /app/sqlite_backups.py check: тот же контроль для Docker HEALTHCHECK,
  без сетевого запроса и без отключения проверки TLS.
- Возраст копии больше 8 часов, heartbeat старше 180 секунд, ошибка создания/
  публикации/ротации или исчезновение файла дают unhealthy. Docker проверяет
  раз в минуту, допускает 120 секунд старта и 3 неудачи.
- Ошибки пишутся фиксированными кодами backup_failed code=..., без данных БД.
  Это локальный контроль/API/Container Station; внешние сообщения не отправляются.

Интервалы: DD_BACKUP_INTERVAL_SECONDS, DD_BACKUP_MAX_AGE_SECONDS,
DD_BACKUP_POLL_SECONDS, DD_BACKUP_RETRY_SECONDS, DD_BACKUP_HEARTBEAT_SECONDS,
DD_BACKUP_KEEP. Невалидные/NaN интервалы отклоняются.

Восстановление: выбрать доступную пару deepdish-*.db и .db.json, проверить SHA-256
и SQLite, затем использовать копию в остановленном/изолированном приложении.
Внешняя файловая копия может поймать границу между поколениями: если status
ссылается на отсутствующую пару, выбрать предыдущее полное поколение; не доверять
одному status. Исторические snapshots без manifest остаются до штатной ротации
и требуют отдельной проверки перед использованием. Работающий основной .db
и WAL не заменяют проверенный snapshot.

Откат к серверу 0.4.6: остановить контейнер, вернуть предыдущий server.py из Git,
вернуть прежний compose при его изменении, запустить контейнер. Основную БД,
сертификаты и snapshots не заменять. Новые JSON не мешают старому серверу.
Перед обновлением сверить текущий код с сохранённым Git и пути bind mounts.

Проверки: python -m unittest discover -s backend -p "test_*backups.py" -v.
Все тесты используют временные вымышленные БД. Production DB не исполняется тестами.
